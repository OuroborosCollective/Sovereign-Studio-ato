01 / DAS PROBLEM

„Erledigt“ ist kein
Beweis.

Ein Sprachmodell kann eine Lösung beschreiben. Ein Tool kann Erfolg melden. Eine Oberfläche kann grün aussehen. Keines davon allein bestätigt, dass der Zielzustand tatsächlich erreicht wurde.

01 — AUTORITÄT
◎

Grenzen vor Effekten

Operationen werden an konkrete Berechtigungen, Werkzeuge, Repositories und Revisionen gebunden. Ohne zulässige Freigabe kein stiller Schreibzugriff.

02 — NACHVOLLZIEHBARKEIT
⌁

Ausführung ist beobachtbar

Jobs, Git-Änderungen, Workflow-Ergebnisse und Receipts werden unterschieden. Textantworten ersetzen keine überprüfbaren Resultate.

03 — VERIFIKATION
◇

Readback statt Behauptung

Der tatsächliche Zielzustand entscheidet über den Nachweis. Fehlt die Prüfung, bleibt das Ergebnis ausdrücklich unbestätigt.

02 / DIE ARCHITEKTUR

Ein Arbeitsraum.
Klare Wahrheitsgrenzen.

Monitor-first statt Chat-Fassade: Das Interface visualisiert den Arbeitsstand. Die Ausführungs- und Evidenzlogik lebt hinter expliziten technischen Grenzen.

01

Live Workspace Monitor

Web-/Android-Oberfläche mit eingebetteter Kommunikation und begrenzten Beobachtungsansichten.

02

Typed Engine Boundary

Absicht wird zu validierten Kommandos. Präsentationstext ändert keinen kanonischen Systemzustand.

03

Agent Runtime & MCP

Isolierte Arbeitsbereiche, GitHub-Operationen, Werkzeugverträge, Policy- und Consent-Gates.

04

Readback & Evidence

Revision, CI, Artefakt, Deployment und tatsächliche Runtime bleiben getrennte Nachweisklassen.

THE OPERATING PRINCIPLE
Runtime creates truth.
UI displays bounded projections.
Evidence decides completion.

Das ist ein Architekturvertrag des Repositories, keine Behauptung, dass jede Funktion aktuell live geprüft wurde.

02 / DIAGNOSE

Bug Investigation & Repair

Ergebnis: Reproduktion · Patch · Regressionstest
